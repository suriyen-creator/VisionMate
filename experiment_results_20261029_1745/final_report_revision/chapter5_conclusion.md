# บทที่ 5: สรุปผลการทดลอง อภิปรายผล และข้อเสนอแนะ (Conclusions, Discussion, and Recommendations)
**โครงงาน:** ระบบผู้ช่วยบรรยายสภาพแวดล้อมและค้นหาสิ่งของสำหรับผู้พิการทางสายตาด้วยเทคโนโลยี Edge AI และ Local LLM บน Raspberry Pi 4  

---

## 5.1 สรุปผลการทดลองเทียบกับวัตถุประสงค์ของโครงงาน (Comparison with Objectives)

จากการดำเนินงาน พัฒนา และทดสอบระบบจริงบนอุปกรณ์ Raspberry Pi 4 Model B (RAM 8 GB) สามารถสรุปผลการทดลองเปรียบเทียบกับวัตถุประสงค์ของโครงงานที่กำหนดไว้ได้ดังนี้:

### 1. การพัฒนาระบบคอมพิวเตอร์วิทัศน์ Edge AI บน Raspberry Pi 4
- **สิ่งที่พิสูจน์ได้จริง:** ระบบสามารถรันโมเดล Object Detection YOLOv8n ONNX บน CPU Quad-core Cortex-A72 แบบ 4 เธรดได้ที่ความเร็วในการอนุมานเฉลี่ย **187.51 ms (~5.3 FPS)** และเมื่อรวมขั้นตอนเปิดกล้อง ตรวจสอบภาพ และประมวลผลก่อน-หลัง ระบบกระบวนการวิทัศน์ทำงานได้ที่เวลารวมเฉลี่ย **275.83 ms (~3.6 FPS)** โดยใช้หน่วยความจำ RAM ของทั้งระบบเพียงประมาณ **2,051–2,056 MB** อุณหภูมิ CPU สูงสุดไม่เกิน **53.0°C** โดยไม่เกิดปัญหาความร้อนสะสมเกินพิกัด (Thermal Throttling) หรือปัญหาหน่วยความจำไม่เพียงพอ (OOM)
- **สิ่งที่ยังไม่สามารถพิสูจน์ได้:** เนื่องจากอุปกรณ์ที่ใช้ทดสอบจริงเป็นรุ่น RAM 8 GB จึงยังไม่สามารถรับรองได้ว่าระบบจะทำงานได้เสถียรในระดับเดียวกันบนบอร์ดรุ่น RAM 4 GB นอกจากนี้ ยังไม่สามารถระบุค่าความแม่นยำในการตรวจจับ (Precision, Recall, F1-score และ mAP@0.5) ได้เนื่องจากยังไม่มีชุดภาพทดสอบพร้อม Annotation พิกัดกรอบจริง

### 2. การระบุชนิด สี ทิศทาง และความสัมพันธ์ของสิ่งของ
- **สิ่งที่พิสูจน์ได้จริง:** ตรรกะโปรแกรมจำแนกสีด้วยระบบ HSV ครอบคลุม 11 แถบสี และตรรกะจัดมุมมองตามหน้าปัดนาฬิกา (ซ้าย 10 นาฬิกา, ตรงหน้า 12 นาฬิกา, ขวา 2 นาฬิกา) ผ่านการทดสอบ Unit Test ทางคณิตศาสตร์ได้อย่างถูกต้อง 100% ตามข้อกำหนด
- **สิ่งที่ยังไม่สามารถพิสูจน์ได้:** การประเมินระยะห่าง "ระยะใกล้", "ระยะกลาง" และ "ระยะไกล" ในปัจจุบันเป็นเพียงการจัดกลุ่มตามขนาด Bounding Box และตำแหน่งพิกเซล ยังไม่มีการสอบเทียบ (Calibration) เทียบกับระยะทางทางกายภาพจริงเป็นหน่วยเซนติเมตรหรือเมตร

### 3. การประยุกต์ใช้ Local LLM เพื่อบรรยายภาพรวมของสภาพแวดล้อม
- **สิ่งที่พิสูจน์ได้จริง:** โมเดลภาษาขนาดเล็ก Qwen2.5-0.5B สามารถทำงานแบบ Local บนบอร์ด Raspberry Pi 4 ผ่าน Ollama API ได้จริงโดยไม่ต้องเชื่อมต่ออินเทอร์เน็ต มีอัตราการสร้างข้อความเฉลี่ยที่ **7.3–10.9 tokens/sec**
- **สิ่งที่ยังไม่สามารถพิสูจน์ได้ / ข้อจำกัดที่ค้นพบ:** เวลาในการสร้างคำบรรยายเฉลี่ยอยู่ที่ **~9.5 วินาที** ซึ่งเกินกว่าเกณฑ์ Timeout 8.0 วินาทีของแอปพลิเคชัน ทำให้ในสภาวะการทำงานจริงระบบเกือบทั้งหมดต้องสลับมาใช้ Python Fallback นอกจากนี้ ยังพบปัญหาภาพหลอน (Hallucination) ในสถานการณ์แสงน้อย ซึ่งโมเดลลอกเลียนแบบประโยคตัวอย่างใน Prompt แทนที่จะใช้ข้อมูลภาพจริง

### 4. การสื่อสารด้วยเสียงและการทำงานแบบไม่ปิดกั้น (Non-blocking Voice UX)
- **สิ่งที่พิสูจน์ได้จริง:** สถาปัตยกรรมมัลติเธรดร่วมกับระบบแคชเสียงใน RAM (`/dev/shm/`) สามารถขับเสียงแจ้งเตือนระบบได้ในเวลา **~0.17 ms** และการสร้างคำบรรยายในโหมด Fast Path ทำงานได้ในเวลารวมประมาณ **~276 ms** ถือเป็นระบบกึ่งเรียลไทม์ (Soft Real-time) ที่ตอบสนองต่อผู้ใช้ได้ในเสี้ยววินาที
- **สิ่งที่ยังไม่สามารถพิสูจน์ได้:** ระบบสังเคราะห์เสียงพูดใหม่ (gTTS) ยังต้องพึ่งพาการเชื่อมต่ออินเทอร์เน็ต (ความหน่วงเฉลี่ย ~370 ms) หากสัญญาณเครือข่ายขาดหายจะไม่สามารถสร้างประโยคเสียงใหม่ที่ไม่เคยแคชไว้ได้

## 5.2 ข้อค้นพบเชิงวิศวกรรมและข้อจำกัดของระบบ (Engineering Insights & Limitations)

### 1. ความจำเป็นอย่างยิ่งยวดของสถาปัตยกรรมแบบไฮบริด (Hybrid Architecture)
ผลการทดลองทางวิศวกรรมพิสูจน์ให้เห็นอย่างชัดเจนว่า **การออกแบบระบบให้มี Fast Path (Python Rule-based) ควบคู่กับ LLM Path เป็นการตัดสินใจที่ถูกต้องและจำเป็นอย่างยิ่ง** เพราะหน่วยประมวลผล ARM Cortex-A72 บน Raspberry Pi 4 ไม่มีหน่วยประมวลผลปัญญาประดิษฐ์เฉพาะทาง (NPU) ทำให้การรันโมเดลภาษาขนาดใหญ่ต้องใช้เวลาเฉลี่ยเกือบ 10 วินาที หากไม่มี Fast Path ที่ทำงานได้ใน 276 ms ระบบจะไม่สามารถแจ้งเตือนสิ่งกีดขวางระยะใกล้ได้ทันเวลา ซึ่งอาจก่อให้เกิดอันตรายต่อผู้พิการทางสายตา

### 2. ขีดจำกัดของโมเดลขนาดเล็ก (0.5B) ในการประมวลผลภาษาไทย
โมเดลขนาด 0.5 พันล้านพารามิเตอร์มีความจุพารามิเตอร์น้อย ทำให้มีข้อจำกัดในการตีความคำสั่งภาษาไทยที่ซับซ้อน จากการทดสอบพบว่าโมเดลเกิดปรากฏการณ์ **Few-shot Anchoring** โดยเลือกที่จะลอกประโยคตัวอย่างในคำสั่ง Prompt มาตอบเมื่อข้อมูลที่ป้อนมีความไม่แน่นอน นอกจากนี้ โครงสร้างตัวตัดคำ (Tokenizer) ของภาษาไทยต้องใช้จำนวนโทเคนต่อคำมากกว่าภาษาอังกฤษ ทำให้ Prompt ภาษาไทยขนาดยาว (252 โทเคน) เข้าใกล้ขีดจำกัด Context Window (256 โทเคน) ของระบบอย่างรวดเร็ว

### 3. ข้อพึงระวังด้านความปลอดภัยในการนำทาง (Critical Safety Disclaimer)
> [!CAUTION]
> **ข้อสรุปด้านความปลอดภัย:**  
> **ห้ามสรุปว่า “ระบบนี้มีความปลอดภัยเพียงพอสำหรับการนำทางผู้พิการทางสายตาในชีวิตประจำวัน” จากผลการทดลองนี้เพียงอย่างเดียว** เนื่องจากระบบยังผ่านการทดสอบเฉพาะในสภาพแวดล้อมห้องทดลองที่มีวัตถุนิ่ง ยังขาดการทดสอบในสภาพแวดล้อมเปิดภายนอกอาคารที่มีสิ่งกีดขวางเคลื่อนไหวเร็ว (เช่น รถยนต์, รถจักรยานยนต์ หรือผู้คนที่เดินสวนทาง) อีกทั้งการประมาณระยะห่างด้วยขนาดภาพ 2 มิติยังไม่ได้รับการรับรองความแม่นยำเทียบเท่าเซนเซอร์วัดระยะทางกายภาพ (เช่น LiDAR หรือ Ultrasonic Sensors)

## 5.3 ข้อเสนอแนะและแนวทางการพัฒนาต่อยอด (Future Work & Recommendations)

เพื่อให้ระบบมีความสมบูรณ์ แม่นยำ และพร้อมสำหรับการใช้งานจริงในระดับสูงขึ้น ผู้จัดทำขอเสนอแนะแนวทางพัฒนาต่อยอดดังนี้:

1. **การจัดทำชุดข้อมูลภาพและ Annotation เพื่อวัดค่าความแม่นยำ (Object Detection Benchmark):**  
   ควรถ่ายภาพสิ่งของในห้องจำลองและพื้นที่ทางเดินจริงจำนวน 30–50 ภาพ พร้อมทำการระบุพิกัดกรอบ Bounding Box มาตรฐาน (เช่น รูปแบบ YOLO หรือ COCO JSON) เพื่อนำมาคำนวณค่า Precision, Recall, F1-score และ mAP@0.5 ให้เป็นตัวเลขสถิติที่ได้รับการยอมรับในเชิงวิชาการ
2. **การสอบเทียบระยะห่างด้วยเครื่องมือวัดทางกายภาพ (Physical Distance Calibration):**  
   ควรนำเครื่องมือวัดระยะทางเลเซอร์ (Laser Distance Meter) มาวัดระยะทางจริงของวัตถุแต่ละชิ้นที่ระยะ 30 ซม., 60 ซม., 100 ซม., 150 ซม. และ 200 ซม. แล้วนำค่าพิกัดพิกเซล $y_{\text{bottom}}$ และขนาดพื้นที่ Bounding Box มาทำสมการถดถอย (Regression Analysis) เพื่อแปลงค่าพิกัดภาพเป็นระยะทางจริงในหน่วยเซนติเมตรได้อย่างแม่นยำ
3. **การทดสอบบนฮาร์ดแวร์ Raspberry Pi 4 รุ่น RAM 4 GB:**  
   ควรนำสคริปต์ Benchmark ไปรันซ้ำบนบอร์ดรุ่น RAM 4 GB เพื่อสังเกตพฤติกรรมการจัดสรรหน่วยความจำและตรวจสอบว่าระบบยังคงทำงานได้โดยไม่เกิด Swap Thrashing หรือ OOM ภายใต้พื้นที่ RAM ที่จำกัดลงครึ่งหนึ่ง
4. **การเปลี่ยนผ่านสู่ระบบ Offline Text-to-Speech 100% (Local TTS):**  
   เพื่อตัดการพึ่งพาการเชื่อมต่ออินเทอร์เน็ตของ gTTS ควรติดตั้งโมเดลสังเคราะห์เสียงภาษาไทยแบบออฟไลน์น้ำหนักเบา เช่น **Piper TTS** หรือ **eSpeak-NG** ซึ่งสามารถสร้างไฟล์เสียงภาษาไทยได้บนเครื่องโดยตรง ทำให้ระบบกลายเป็น Edge AI ที่ทำงานแบบ Standalone ได้อย่างแท้จริง
5. **การปรับแต่ง Prompt และจูน Local LLM (Prompt & Model Optimization):**  
   ควรปรับแต่ง Prompt ให้สั้นกระชับลงโดยตัดตัวอย่าง Few-shot ออกเพื่อลดขนาดโทเคนให้อยู่ในระดับต่ำกว่า 100 โทเคน และขยายขอบเขต Context Window ใน Ollama เป็น `num_ctx: 512` เพื่อป้องกันปัญหา Context Shift นอกจากนี้ ควรพิจารณา Fine-tune โมเดลขนาด 0.5B ด้วยชุดข้อมูลคำสั่งภาษาไทยสำหรับการบรรยายภาพโดยเฉพาะ เพื่อลดปัญหาภาพหลอนและเพิ่มความถูกต้องของไวยากรณ์
6. **การประเมินผลโดยกลุ่มผู้พิการทางสายตาจริง (Human-Centered Usability Testing):**  
   ควรจัดให้มีการทดสอบความพึงพอใจและการใช้งานจริงร่วมกับกลุ่มตัวอย่างผู้พิการทางสายตา ภายใต้การควบคุมและดูแลความปลอดภัยอย่างใกล้ชิด เพื่อประเมินคะแนน Mean Opinion Score (MOS) ด้านความชัดเจนของคำบรรยาย ความดังของเสียง และความมั่นใจของผู้ใช้ในขณะเคลื่อนที่
