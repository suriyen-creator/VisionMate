## 4.1 ผลการทดสอบเวลาในการประมวลผล (Component Latency Benchmark)

การประเมินเวลาในการประมวลผลของระบบดำเนินการบนอุปกรณ์ Raspberry Pi 4 Model B (RAM 8 GB) เครื่องจริง โดยแบ่งการวัดออกเป็นส่วนประกอบย่อยทางคอมพิวเตอร์วิทัศน์ การสร้างคำบรรยาย และการจัดการสัญญาณเสียง ข้อมูลดิบถูกบันทึกในไฟล์ `latency_raw.csv` จำนวน 290 เรคคอร์ด และ `llm_evaluation.csv` จำนวน 7 สถานการณ์

ในการวิเคราะห์ทางสถิติ ผู้ตรวจสอบได้จำแนกประเภทข้อมูลออกเป็น 3 ระดับอย่างโปร่งใส:
1. **ค่าที่วัดได้จริงโดยตรง (Directly Measured):** เวลาของแต่ละขั้นตอนย่อยที่จับเวลาด้วย `time.perf_counter()`
2. **ค่าที่คำนวณจากข้อมูลดิบต่อรอบจริง (Per-iteration Recalculated):** เวลารวมของขั้นตอนวิทัศน์ในแต่ละรอบ ($t_{\text{total}, i} = \sum_{k} t_{k, i}$)
3. **ค่าประมาณการผลรวมขั้นตอนย่อย (Additive Synthetic Estimate):** ค่าเวลารวมตั้งแต่ต้นทางถึงปลายทาง (End-to-End Latency)

### การวิเคราะห์ผลการวัดเวลา:
1. **การแยกแยะระหว่าง YOLO Inference และ Vision Pipeline:**  
   เวลาเฉพาะการประมวลผลโมเดลโครงข่ายประสาทเทียม YOLOv8n ONNX บน CPU 4 คอร์มีค่าเฉลี่ยอยู่ที่ **187.51 ms (~5.3 FPS)** แต่เมื่อรวมขั้นตอนเปิดกล้อง (40.66 ms), ตรวจสอบความสว่างและความเบลอ (10.31 ms), Preprocessing (4.85 ms), Postprocessing NMS (28.84 ms), และสกัดสี/ทิศทาง (3.67 ms) เวลารวมของกระบวนการวิทัศน์จริงต่อรอบมีค่าเฉลี่ยอยู่ที่ **275.83 ms** หรือคิดเป็นอัตราการประมวลผลเฟรมภาพสดที่ **~3.6 FPS** ซึ่งถือเป็นความเร็วการทำงานจริงของระบบ Edge AI บนฮาร์ดแวร์นี้
2. **ความเร็วของการสร้างประโยคด้วยกฎ (Fast Path Narrative):**  
   การประกอบข้อความด้วย Python Rule-based ใช้เวลาเฉลี่ยเพียง **0.002 ms (2 ไมโครวินาที)** ถือเป็นการประมวลผลระดับต่ำกว่ามิลลิวินาที (Sub-millisecond) ที่ไม่ก่อให้เกิดภาระความหน่วงในระบบ
3. **ขอบเขตการวัดเวลาของระบบเสียง (Software-Level Audio Latency):**  
   - การดึงไฟล์เสียงที่แคชไว้แล้วใน RAM (`/dev/shm/`) ใช้เวลาเพียง **0.05 ms**
   - การโหลดไฟล์เสียงเข้าสู่บัฟเฟอร์เสียงของ Pygame (`pygame.mixer.music.load`) ใช้เวลาเฉลี่ย **0.12 ms**
   - การสร้างไฟล์เสียงใหม่ผ่าน Google TTS (gTTS) ใช้เวลาเฉลี่ย **370.32 ms**  
   *(ข้อพึงระวังทางวิชาการ: เวลาในแถวที่ 9–11 ทั้งหมดเป็นการวัดเวลาในระดับซอฟต์แวร์ ยังไม่รวมเวลาการแปลงสัญญาณดิจิทัลเป็นอนาล็อกของชิป DAC หรือเวลาที่คลื่นเสียงเดินทางผ่านอากาศมายังหูของผู้ใช้งานจริง)*
4. **ความแตกต่างของชุดทดสอบ Local LLM (แถวที่ 12 เทียบกับ 13):**  
   - ในชุดทดสอบ Latency 10 รอบ (แถว 13) ซึ่งใช้ Prompt ภาษาไทยเต็มรูปแบบขนาดยาว (252 โทเคน) Ollama ไม่สามารถประมวลผลเสร็จสิ้นได้ทันเวลา Client Timeout ที่ตั้งไว้ 12 วินาที (เกิด Timeout 100%)
   - ในชุดทดสอบคุณภาพ 7 สถานการณ์ (แถว 12) ซึ่งตั้งเวลา Timeout ไว้ 35 วินาที โมเดลสามารถสร้างคำตอบได้สำเร็จครบทั้ง 7 สถานการณ์ โดยมีเวลาตอบสนองเฉลี่ย **9,533.2 ms (~9.5 วินาที)** ซึ่งยืนยันว่าการทำงานของโมเดลขนาด 0.5B บน CPU มีเวลาตอบสนองอยู่ในระดับ 9–11 วินาทีเป็นปกติ

## 4.2 การเปรียบเทียบ End-to-End Latency ระหว่าง Fast Path และ LLM Path

เพื่อประเมินความพร้อมในการใช้งานจริง ระบบได้รับการออกแบบโครงสร้างแบบไฮบริด โดยเมื่อนำเวลาเฉลี่ยของขั้นตอนย่อยมารวมกัน (Additive Stage-wise Synthetic Estimate) จะได้ผลเปรียบเทียบดังแสดงในตารางที่ 4.2:

### ตารางที่ 4.2: การเปรียบเทียบเวลารวมประมาณการ (Estimated End-to-End Latency)
| เส้นทางการประมวลผล (Processing Path) | เวลาประมวลผลภาพ (Vision) | เวลาสร้างคำบรรยาย (Narrative) | เวลาเตรียมสัญญาณเสียง (Audio) | เวลารวม End-to-End (ประมาณการ) | อัตราเทียบเท่า | ความเหมาะสมในการใช้งานจริง |
| :--- | :---: | :---: | :---: | :---: | :---: | :--- |
| **Fast Path (หาของด่วน / วัตถุ 1–2 ชิ้น)** | 275.83 ms | 0.002 ms | 0.17 ms (RAM Cache) | **~276 ms** | **~3.6 FPS** | **เหมาะสำหรับการเตือนสิ่งกีดขวางระยะประชิดทันท่วงที** |
| **LLM Path (บรรยายสภาพแวดล้อมภาพรวม)** | 275.83 ms | 9,533.20 ms | 370.44 ms (gTTS) | **~10,179 ms (~10.2 วินาที)** | **~0.1 FPS** | **เหมาะสำหรับการขอคำอธิบายสภาพห้องเมื่อผู้ใช้หยุดนิ่ง** |

จากการวิเคราะห์เปรียบเทียบ:
- **Fast Path** ใช้เวลาเพียง **~276 ms** (เสี้ยววินาที) จัดเป็นระบบกึ่งเรียลไทม์ (Soft Real-time) ที่สามารถแจ้งเตือนสิ่งของที่อยู่ตรงหน้าหรือระยะเอื้อมมือถึงได้ทันเวลา ช่วยป้องกันไม่ให้ผู้พิการทางสายตาชนสิ่งกีดขวาง
- **LLM Path** ใช้เวลารวมมากกว่า **10 วินาที** จึงไม่สามารถนำมาใช้เป็นระบบนำทางแบบต่อเนื่อง (Continuous Navigation) ได้ แต่มีประโยชน์ในฐานะผู้ช่วยสังเคราะห์ภาพรวมของห้องเมื่อผู้ใช้สั่งการและหยุดยืนนิ่ง

การวัดอัตราการใช้ทรัพยากรระบบดำเนินการด้วยสคริปต์อัตโนมัติ บันทึกข้อมูลที่ความถี่ 1 Hz จำนวน 90 วินาที ครอบคลุม 4 สภาวะการทำงานต่อเนื่อง โดยผลการวัดจริงบนบอร์ด Raspberry Pi 4 Model B (RAM 8 GB) สรุปได้ดังตารางที่ 4.3:

### การวิเคราะห์ผลด้านทรัพยากร:
1. **การใช้หน่วยความจำ RAM และคำอธิบายสูตรเปอร์เซ็นต์:**  
   ระบบทั้งหมดใช้ RAM คงที่อยู่ที่ประมาณ **2,048 MB ถึง 2,056 MB** โดยบอร์ดที่ใช้ทดสอบมี RAM รวม 7,819.8 MB (7.63 GiB) หากคำนวณสัดส่วนตรงไปตรงมา:
   $$\text{Raw Ratio} = \frac{\text{RAM Used}}{\text{Total RAM}} \times 100 = \frac{2,055.9}{7,819.8} \times 100 = \mathbf{26.29\%}$$
   อย่างไรก็ตาม ในคอลัมน์สัดส่วน RAM มีค่าเท่ากับ **27.37% (27.4%)** เนื่องจากฟังก์ชัน `psutil.virtual_memory().percent` ในระบบปฏิบัติการลินุกซ์คำนวณตามสูตร Memory Commitment ซึ่งนำหน่วยความจำว่างจริงที่ระบบจัดสรรได้ (Available Memory ซึ่งรวมส่วนบัฟเฟอร์ที่ปลดปล่อยไม่ได้ทันที) มาคำนวณ:
   $$\text{Commitment Percentage} = \frac{\text{Total} - \text{Available}}{\text{Total}} \times 100 = \frac{7,819.8 - 5,678.4}{7,819.8} \times 100 = \mathbf{27.38\%}$$
   ทั้งสองค่าพิสูจน์ได้ว่าระบบมีหน่วยความจำคงเหลือว่างมากกว่า **5.6 GB** ตลอดการทำงาน
2. **การใช้งาน Swap Memory:**  
   ตลอดการทดสอบ 90 วินาที ค่า Swap มีค่าเป็น **0.0 MB ตลอดเวลา** บ่งชี้ว่าหน่วยความจำกายภาพของเครื่องรุ่น 8 GB มีความจุเกินพอสำหรับระบบนี้ ทำให้ไม่เกิดปัญหาหน่วงจากการสลับหน้าหน่วยความจำลงดิสก์ (Disk Swapping) หรือปัญหา Out-Of-Memory (OOM)
3. **การทำงานของ CPU และความร้อน:**  
   - ค่า CPU Usage ในตารางเป็น **System-Wide Aggregate CPU Utilization** (การใช้งานเฉลี่ยรวม 4 คอร์) เมื่อเปิดระบบ YOLO หรือ LLM ค่า CPU พุ่งสูงถึง 98–100% ยืนยันว่าเธรดคำนวณ 4 เธรดของ ONNX Runtime และ Ollama เข้าใช้งานคอร์ของ Cortex-A72 อย่างเต็มขีดความสามารถ
   - อุณหภูมิ CPU ไต่ระดับจาก 41.1°C ในสภาวะ Idle ขึ้นไปสูงสุดที่ **53.0°C** ในสภาวะ Complete Pipeline ซึ่งยังต่ำกว่าขีดจำกัดความปลอดภัย 75.0°C และห่างจากจุดวิกฤต Thermal Throttling ของ Raspberry Pi 4 (80.0°C) ถึง 27°C
   - ค่าสถานะ Throttling ของระบบฮาร์ดแวร์คงค่า **`0x0` ทุกวินาที** ยืนยันว่าไม่เกิดอาการลดความถี่สัญญาณนาฬิกาหรือไฟตกในระหว่างทดลอง

### บทวิเคราะห์เชิงวิศวกรรมต่อผลการทำงานของ LLM:
1. **การเกิดภาพหลอนจากการยึดติดตัวอย่าง (Few-shot Anchoring Hallucination):**  
   ในสถานการณ์ S5 ซึ่งภาพมีสภาพ "ค่อนข้างมืด" และมี "ขวดน้ำสีดำ" โมเดลกลับสร้างประโยคตอบว่า *"ห้องนี้แสงสว่างปกติครับ มีแก้วน้ำสีแดงวางอยู่บนโต๊ะทางขวามือ..."* ซึ่งตรงกับตัวอย่าง Few-shot ในคำสั่ง Prompt ทุกประการ ปรากฏการณ์นี้ชี้ให้เห็นว่าโมเดลขนาด 0.5 พันล้านพารามิเตอร์มีความจุทางปัญญา (Cognitive Capacity) จำกัด และมีแนวโน้มที่จะลอกเลียนแบบข้อความตัวอย่างเมื่อพบอินพุตภาษาไทยที่มีความขัดแย้ง
2. **การวิเคราะห์สาเหตุของความล่าช้าและบริบท (Context Window vs CPU Compute Limit):**  
   - จากการตรวจสอบบันทึกของ Ollama Systemd Service (`journalctl -u ollama`) ยืนยันข้อเท็จจริงว่า Prompt ภาษาไทยพร้อมตัวอย่างมีขนาด **252 โทเคน** ในขณะที่ค่า `num_ctx` ใน `app.py` กำหนดไว้ที่ **256 โทเคน** (ใช้งานไปถึง 98.4% ของ Context Window) ทำให้ระบบต้องทำ `slot context shift` สลับหน่วยความจำบริบท
   - **อย่างไรก็ตาม การวิเคราะห์ทางวิศวกรรมชี้ว่า Context Saturation เป็นเพียง "ปัจจัยร่วมที่มีหลักฐานสนับสนุน (Supported Contributing Factor)"** เพราะในการทดลองควบคุมโดยใช้ Prompt สั้นขนาด 70 โทเคน โมเดลก็ยังต้องใช้เวลาประมวลผลประมาณ 8.4 วินาที ดังนั้น **ขีดจำกัดด้านกำลังการประมวลผลของ CPU Cortex-A72 (Compute-bound throughput ~7.3–10.9 tokens/sec)** จึงเป็นสาเหตุหลักร่วมกันที่ทำให้เวลาตอบสนองเกินเกณฑ์ Timeout 8.0 วินาทีของแอปพลิเคชัน

## 4.5 การตรวจสอบตรรกะโปรแกรมคอมพิวเตอร์วิทัศน์ (Computer Vision Component Verification)

เพื่อประเมินความถูกต้องของกฎและขั้นตอนวิธีที่พัฒนาขึ้นในส่วนของ Computer Vision ได้มีการจัดทำชุดทดสอบระดับฟังก์ชัน (Unit Logic Tests) แยกต่างหากดังสรุปในตารางที่ 4.5:

### ตารางที่ 4.5: สรุปผลการทดสอบตรรกะโปรแกรมและสถานะการวัดผลในภาพจริง

### การจำแนกประเภทและข้อจำกัดสำคัญ:
1. **ผลทดสอบ Color, Direction, Distance และ Surface:**  
   ผลการทดสอบที่ผ่าน 100% เป็นผลจากการทดสอบ **Unit Test เชิงคณิตศาสตร์และตรรกะเงื่อนไข (Mathematical & Logic Verification)** โดยใช้ข้อมูลอินพุตจำลองเพื่อพิสูจน์ว่าฟังก์ชันในโปรแกรมทำงานถูกต้องตามที่นิยามไว้ **แต่ไม่สามารถนำผลนี้ไปอ้างว่าเป็นความแม่นยำ 100% ของระบบในสภาพแวดล้อมจริงได้** เนื่องจากในสภาพแวดล้อมจริงจะมีแสงสะท้อน แสงเงา และมุมกล้องที่แปรปรวน
2. **การไม่สามารถรายงานค่า Precision, Recall, F1-score และ mAP@0.5:**  
   เนื่องจากในระบบปัจจุบันยังไม่มีชุดภาพทดสอบที่มีการทำ Label และระบุพิกัดกรอบสี่เหลี่ยมจริง (Ground Truth Annotation) ในสภาพแวดล้อมห้องทดลอง **โครงงานนี้จึงไม่สามารถระบุตัวเลข mAP หรือความแม่นยำในการตรวจจับได้ และได้ระบุสถานะเป็น NOT MEASURED / INSUFFICIENT DATA** เพื่อรักษาความซื่อสัตย์ทางวิชาการและไม่กุตัวเลขขึ้นเอง
